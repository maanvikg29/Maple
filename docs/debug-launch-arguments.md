# DEBUG launch arguments

DEBUG builds read these arguments, which `xcrun simctl launch <udid> com.maanvikgupta.maple <args…>` passes, so any screen state can be reached for screenshots without tapping through the app. Release builds ignore all of them. They arrive through the `UserDefaults` argument domain (`-Key value`).

| Argument | Values | Owner | Effect |
|---|---|---|---|
| `-MapleDemoTab` | `home`, `rest`, `herbarium` | App (`RootView`) | Opens on that tab. |
| `-MapleDemoSpecies` | `0`…`155` | Core (`DemoData`) | Opens with a deterministic demo collection of that many species (default 23 when only `-MapleDemoDays` or `-MapleDemoWaiting` is given), held in memory, with the standard schedule saved. The cheapest rungs come first, so the counters match the ladders; the Sugar maple is always there. `0` is an empty collection. The real collection file is never touched. |
| `-MapleDemoDays` | integer | Core | Tended days for the demo collection (default 41), which drive tree growth `g`. Unlock dates spread over about 1.6 × this many days, so pressed colourways mix seasons. |
| `-MapleDemoWaiting` | integer | Core | Number of earned leaves still waiting to be revealed: the newest ones, never the Sugar maple. They can be opened in morning, day and evening. |
| `-MapleDemoPhase` | `morning`, `day`, `evening`, `windDown`, `night` | Core (clock) | Freezes `\.mapleClock` at a time inside that phase of today (or `-MapleDemoDay`): morning from last night's wake-up, evening on from tonight's schedule, so a weekend night uses the weekend times. The wireframe moments where they fit (evening 1h 20m before wind-down, wind-down 38m before bed), otherwise mid-window. |
| `-MapleDemoSeason` | `spring`, `summer`, `autumn`, `winter` | Core (app wiring) | Overrides the season (`\.season` and the tree inputs). |
| `-MapleDemoRarity` | `YES` | Core | Uses `PreviewLeafShareProvider` (12,480 members, tier-correlated shares) with consent on, so "% of members" values show. |
| `-MapleDemoFresh` | `YES` | Core | Opens with an empty collection and no saved schedule, as on first run. Wins over `-MapleDemoSpecies`. |
| `-MapleDemoPermissions` | `none`, `health`, `all` | Core | Granted permissions: `health` is Apple Health plus a sleep tracker, `all` adds Screen Time. Without it, demo collections (`-MapleDemoSpecies`/`Days`/`Waiting`) are granted `health`, so they show earned progress; `-MapleDemoFresh` gets `none`; any other launch keeps the member's own Apple Health record (`none` until they have been through Apple's prompt). Use `none` to see the "Needs Apple Health" states. Only DEBUG demos can grant a permission this way; the live app grants Apple Health only once the member has answered Apple's prompt. |
| `-MapleDemoSchedule` | `HH:MM-HH:MM`, optionally `/minutes` (e.g. `00:30-08:30/60`) | Core (`DemoLaunchOptions`, added for Rest) | Replaces the saved sleep schedule with this one every night (bedtime-wake, wind-down length; 45 minutes when left out), in memory. `-MapleDemoPhase` then freezes the clock inside that schedule's phase. Ignored with `-MapleDemoFresh`. |
| `-MapleDemoWeekendSchedule` | same format (e.g. `00:30-09:00/60`) | Core (`DemoLaunchOptions`) | Gives the saved schedule a separate weekend: these times on weekend nights (the nights that wake into the calendar's weekend), and `-MapleDemoSchedule` (or the saved/standard weekday times) on the others. In memory; ignored with `-MapleDemoFresh`. |
| `-MapleDemoDay` | a weekday name (`friday`) or `yyyy-MM-dd` | Core (clock) | With `-MapleDemoPhase`: freezes the clock on that day instead of today (a weekday name means the next one, today included), so a weekend night's evening can be shown on any day. Without `-MapleDemoPhase` it does nothing. |
| `-MapleDemoGoodnight` | `YES` | Rest (`WindDownView`) | Wind-down mode opens as if Goodnight had just been tapped: "Phone down at …", then black 10 seconds after launch. Pair it with `-MapleDemoPresent winddown`. (Goodnight only logs the phone-down time; it never earns a leaf.) |
| `-MapleDemoHealthContinue` | `YES` | Health (`HealthPrimerSheet`) | Taps "Continue" on the Apple Health primer a second after it opens, so Apple's Health sheet appears for a screenshot. Pair it with `-MapleDemoPresent health`. On a launch without Core arguments this is the member's real prompt. |
| `-MapleDemoPresent` | see below | Each feature, in its own root view | Opens one sheet, cover or push on launch. |
| `-MapleDemoProfile` | `settings`, `privacy`, `rarity`, `about`, `design` | Profile (`ProfileView`) | With `-MapleDemoPresent profile`: opens the Profile sheet pushed to that page. `rarity` opens Privacy and then its "How rarity works" explainer sheet; `design` is the DEBUG design system screen. |
| `-MapleDemoDesignSection` | `colours`, `surfaces`, `type`, `controls`, `specimens`, `rarity`, `cells`, `trees`, `species` | Profile (`DesignSystemView`) | With `-MapleDemoProfile design`: scrolls the design system screen to that section once it opens. |
| `-MapleDemoScroll` | a category id (e.g. `steady_mornings`) or `dormant` | Herbarium | With `-MapleDemoTab herbarium`: scrolls the grid until that section's header is pinned at the top. |
| `-MapleDemoRevealAt` | seconds, e.g. `0.3`, `0.9`, `1.6`, `3` | Reveal (`RevealDemoOptions`) | Taps the first bud open on launch and freezes the ritual that many seconds after the tap, so mid-frames can be screenshotted. Also freezes the onboarding end's reveal with `-MapleDemoOnboardingStep reveal`. |
| `-MapleDemoRevealOpenAll` | seconds, e.g. `0.5`, `4` | Reveal | Opens the first leaf, taps "Open all" and freezes that many seconds into it (`0.5` the row mid-opening, `4` the list). Needs `-MapleDemoWaiting 2` or more. |
| `-MapleDemoRevealConsent` | `YES` | Reveal | Opens the first leaf and shows the rarity consent sheet over it. |
| `-MapleDemoRevealLeaf` | species id | Reveal | The waiting leaf `-MapleDemoPresent reveal` opens first (`RevealFlow(startingWith:)`); ignored when it isn't waiting. |
| `-MapleDemoReduceMotion` | `YES` | Reveal, Onboarding | The reveal and the onboarding end render as under Reduce Motion (0.6 s crossfade; "Open all" goes straight to the list). `simctl ui` has no Reduce Motion switch. |
| `-MapleDemoFirstRunAutoplay` | seconds, e.g. `3` | Onboarding (`PlantYourMapleView`) | Taps through the real first run on its own, pausing that long on each screen: "Continue" on each question (keeping its default answer), "Save schedule" on the proposed schedule, "Not now" on the Apple Health primer (Apple's own sheet needs a real tap), the notifications step (a placeholder that moves on by itself), then the amber bud and "Place on your maple" once the reveal has settled, and Home opens. Unlike the other onboarding arguments it acts on a live launch (no Core arguments), so it writes the member's files exactly as the taps would (`onboarding.json`, `schedule.json`, settings' sleep goal): use it on a fresh install to screenshot the first run end to end. Killing the app part-way and launching again (with or without it) resumes on the same screen. |
| `-MapleDemoOnboardingStep` | `wake`, `weekend`, `weekend:later`, `sleep`, `winddown`, `schedule`, `schedule:weekend`, `health`, `notifications`, `seed`, `sprout`, `reveal`, `placed` | Onboarding (`PlantYourMapleView`) | Opens onboarding on one screen, in memory. The setup screens: `wake` (weekday wake-up), `weekend` ("And on weekends?" on Same time), `weekend:later` (on Later, with its wheel), `sleep` (sleep need), `winddown`, `schedule` (the schedule proposed from the default answers), `schedule:weekend` (the proposal with a 09:00 weekend wake-up, so the Weekdays · Weekends capsule shows), `health` (the Apple Health primer step, after saving the proposal) and `notifications` (its placeholder, which continues at once). The end, past the schedule step (the default schedule saved): `seed` holds the neutral bud, `sprout` lets it turn amber, `reveal` opens the Sugar maple (freeze it with `-MapleDemoRevealAt`), `placed` shows the grafted seedling and stays there. Pair with `-MapleDemoFresh YES -MapleDemoPresent onboarding`. |
| `-MapleDemoSeedHealth` | number of nights, e.g. `10` | Health (`HealthSleepSeeder`, `HealthDemoSeeding`) | Writes plausible synthetic sleep for the last N complete nights into the simulator's Apple Health, then connects Apple Health and imports, as the real flow would. Nights vary around the saved schedule (each week one late night, one short night and one early one) and none starts before the maple was planted, so the install night counts if it has passed; earlier nights are written but earn nothing (no backfill). Seeding again first deletes the samples an earlier seeding wrote, which the importer sees as deletions. It asks for Apple Health access to write sleep first: **Apple's sheet needs a tap** (and the simulator's Health service can take several seconds to start; a first request may time out). Needs a planted maple. |
| `-MapleDemoSeedSource` | `watch` (default), `iphone`, `otherApp` | Health | What the seeded nights stand for: Apple Watch stages (source A), iPhone's in-bed estimate (C), or another app's asleep samples (B). |
| `-MapleDemoSeedStore` | `health` (default), `memory` | Health (`HealthSleepImporter.launch`) | `memory`, on a demo launch only (any Core argument, so every store is in memory): skips HealthKit and Apple's sheet; the importer's in-memory cache starts with the same samples, as if just read from Apple Health, and they are recorded before the first frame. For automated screenshots. Pair it with `-MapleDemoPermissions health` so Apple Health counts as connected. |
| `-MapleDemoVitality` | `0.4`…`1` | Home (`HomeContent`) | Draws Home's tree and the Tree view at that vitality; `0.45` is the quiet tree (spec §4.8). Nothing is recorded, so it never touches the collection. |

`-MapleDemoPresent` values:
- **App-level** (`App/DemoPresenter.swift`, over any tab): `reveal` (cover), `profile` (sheet; add `-MapleDemoProfile` for a page inside it), `winddown` (cover). `onboarding` makes `RootView` open on the end of onboarding instead of the tabs (pair it with `-MapleDemoFresh YES`; with an already planted collection it goes straight to Home).
- **Home:** `tree` (Tree view), `tree:<speciesID>` (Tree view zoomed onto that leaf, as "Show on my maple"), `streak` (Streak sheet), `leaf:<speciesID>` (leaf detail pushed from Home), `health` (the Apple Health primer, as "Turn on Apple Health" opens it)
- **Herbarium:** `leaf:<speciesID>` (pushes leaf detail), `share:<speciesID>` (leaf detail, then the rendered share-card PNG at its point size), `rarity` (leaf detail of the rarest earned leaf, or the featured one, with the rarity explainer open), `filter`, `search` or `search:<query>` (the Search sheet, already searching)
- **Rest:** `schedule` (the schedule editor at `.medium`, on Every day or tonight's nights), `schedule:bedtime` and `schedule:wake` (the editor at `.large` with that time's wheel open), `schedule:everyday`, `schedule:weekdays` and `schedule:weekends` (the editor on that segment; pair the last two with `-MapleDemoWeekendSchedule` to see a separate weekend)

Feature-level values are checked only by the feature that owns them, on its own tab, so combine them with `-MapleDemoTab`.

**First run.** Without demo arguments the app opens on onboarding (`PlantYourMapleView`, full screen, no tabs: the four questions, the proposed schedule, the Apple Health and notifications primers, then the sprout and the reveal) until the First-steps leaf has been revealed and placed, resuming on the screen it was left on (`onboarding.json`, `OnboardingStore`); `-MapleDemoFresh YES` shows the same first run in memory. Demo collections (`-MapleDemoSpecies`/`Days`/`Waiting`) are already planted and open on the tabs.

Any Core argument makes the launch a demo: every store (collection, schedule, rarity cache, settings, Apple Health record) is held in memory, so nothing a demo does is ever saved. With only `-MapleDemoPhase`, `-MapleDemoSeason`, `-MapleDemoRarity`, `-MapleDemoPermissions` or `-MapleDemoSchedule`, the stores start from an in-memory copy of the member's own files. The wiring is `MapleStores.make(_:)` in MapleServices (settings: `AppSettings.launch()`). Any `-MapleDemo…` argument also keeps wind-down mode's log (`bedside.json`) in memory.

Rest example (a non-default schedule in wind-down): `xcrun simctl launch booted com.maanvikgupta.maple -MapleDemoTab rest -MapleDemoSpecies 23 -MapleDemoPhase windDown -MapleDemoSchedule 00:30-08:30/60`

Weekend examples: `-MapleDemoSpecies 23 -MapleDemoWeekendSchedule 00:30-09:00/60 -MapleDemoDay friday -MapleDemoPhase evening` is Home on a weekend night's evening (add `-MapleDemoTab rest` for the dial, with "Weekdays 23:00 → 07:00" under it); `-MapleDemoDay wednesday` is a weekday night ("Weekends 00:30 → 09:00").

The Reveal and Onboarding arguments act only on a demo launch (with at least one Core argument), so they never touch the member's files. Three exceptions act on a live launch on purpose, as a tap would: `-MapleDemoFirstRunAutoplay`, `-MapleDemoHealthContinue` and `-MapleDemoSeedHealth` (whose samples go into the simulator's Apple Health; the seed arguments never make a launch a demo).

Apple Health end to end (iPhone 17e): a real install and first run (`-MapleDemoFirstRunAutoplay 2`, below), then after midnight `xcrun simctl launch <udid> com.maanvikgupta.maple -MapleDemoPhase morning -MapleDemoPermissions health -MapleDemoSeedHealth 10 -MapleDemoSeedStore memory` shows Home's morning numeral from last night's seeded Watch sleep and the leaves the install night earned waiting; add `-MapleDemoTab herbarium` for the Herbarium, or `-MapleDemoPresent reveal` to open them. Without `-MapleDemoSeedStore memory` (and without Core arguments) the seeder writes into the simulator's Apple Health and the member's own files are used, which needs one tap on Apple's sheet.

Fresh install, real first run (no Core arguments): `xcrun simctl uninstall booted com.maanvikgupta.maple`, install, then `xcrun simctl launch booted com.maanvikgupta.maple -MapleDemoFirstRunAutoplay 3` shows the four questions, the proposed schedule, the Apple Health primer (answered "Not now"), the sprout, the Sugar maple's reveal and then the live Home without Apple Health (the needs-permission next-leaf row). A later launch with `-MapleDemoPresent health` opens the real primer.

Example: `xcrun simctl launch booted com.maanvikgupta.maple -MapleDemoSpecies 23 -MapleDemoDays 41 -MapleDemoWaiting 1 -MapleDemoPhase morning`

No Apple Health (the designed needs-permission states): `-MapleDemoSpecies 1 -MapleDemoPermissions none -MapleDemoPhase evening` shows Home with only the Sugar maple and the needs-permission next-leaf row; add `-MapleDemoTab herbarium` for the Herbarium's "Needs Apple Health" sections, or `-MapleDemoPresent health` for the primer.

Example (Privacy with consent on): `xcrun simctl launch booted com.maanvikgupta.maple -MapleDemoSpecies 23 -MapleDemoRarity YES -MapleDemoPresent profile -MapleDemoProfile privacy`

Reveal examples (the demo collection's newest leaves are the waiting ones): `-MapleDemoSpecies 23 -MapleDemoWaiting 3 -MapleDemoPhase morning -MapleDemoPresent reveal` opens three common leaves (short ritual, "Open all 3"); `-MapleDemoSpecies 80 -MapleDemoWaiting 1` makes the waiting leaf the legendary Smoothbark maple (full ritual); `-MapleDemoSpecies 40 -MapleDemoWaiting 1` an uncommon, approximate one.
